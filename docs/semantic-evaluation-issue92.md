# #92 意味的評価と元観測ごとの推論予算

生成に使った1回と独立評価9回を、同じ元観測・候補・評価manifestへ固定する。
既存の通常入口を無承認で10回へ切り替えず、意味的評価の送信計画と別の承認がある場合だけ9試行を開始する。
採用済みB案と依存順は [共通設計](candidate-evaluation-issue86.md) と親 #83、子 #92 を参照する。

Risk Tier: HIGH。独立したクラウド評価、耐久的な予算、停止・承認の境界を扱う。
実装検証は模擬輸送と通信遮断Dockerで行い、実推論0・追加費用0円。新しい認証取得・実通信・採用・定期有効化は行わない。

## 適用対象と判定

初期の意味的判定器は、登録済み event-status-counts-v1 のツール不要の入出力契約を扱う。
#86のコード評価が合格し、SKILL.mdの変更だけが意味的評価待ちになった候補を受け付ける。
コード不合格、不安定、未登録の契約、Skill未変更は受け付けず、新規推論を始めない。コードだけの合格候補は#86の承認待ちをそのまま使う。
他の手順・分析・振り分けを追加する場合も、登録された判定器・公開契約・独立ケースをPRで追加する。モデルに採点基準や評価コマンドを作らせない。

評価入力は、候補生成前に#86で凍結した独立ケースから選ぶ。同じ入力でbaseline / candidate / 劣化対照を各3回、新しい空のHermesプロファイルで実行する。
SKILL.mdの許可された内容を実際の評価入力へ渡す。各回の順番は巡回し、roleをモデルへ採点ラベルとして渡さない。
入力と正解・個別結果は生成側へ渡さず、正解はhostの判定器だけが使う。実データ・秘密・会話履歴・実Memoryは使わない。

合否は厳密JSONと決定的な正解比較で求め、モデルの自己採点や説明を採用しない。
候補3試行の正解、baselineからの改善、回帰なし、既存の待ち時間/費用条件、3試行の安定性、劣化対照の不正解を確認したときだけ人間承認待ちへ渡す。
構造だけの改善、同点、対照不成立、不安定はHOLD。失敗はREJECTEDまたはSTOPPEDとして区別し、未確認を合格扱いしない。
この有限な契約の結果を、全Skillsの品質や実CI障害の原因確定とは報告しない。

## 予算と停止

- 元観測は#85の完了receipt、#86の候補/評価hashで確認する。別eventへ複製した記録では同じ生成に対する追加予算を作れない。
- 生成1回を消費済みとし、固定の9枠（roleごと3）だけを許可する。各送信前に排他的なintentを保存し、ファイルとディレクトリを同期する。
- 同時1、再送0、各応答30秒。#86で使用した機械時間を引き継ぎ、残り1200秒以内で実行する。
- 1回のキャンペーンは再開・リセットしない。認証拒否、枠不足、期限・承認不一致、途中失敗、送信結果不明も消費済みとし、勝手に再試行しない。
- 生成と共有のcontroller lockを使う。stopは許可されたintent・固定コンテナ設定を照合し、検査したコンテナIDだけを停止する。
- 後始末不明のpendingは残し、通常生成とresumeも拒否する。明示的な確認前に削除しない。認証更新、別アカウント・API課金へのfallbackは追加しない。

認証の保管範囲は既存の試験専用プロファイルのまま。承認前には読み込まない。
実行時も認証値はstdinとコンテナtmpfsだけへ渡し、引数・環境変数・永続ログに出さない。
追加費用0円はPlus利用枠・追加クレジットOFFを実通信前に確認した条件であり、サーバーの請求額を自動照会したという意味ではない。

## 操作と記録

1. `scripts/evaluate_skill_semantics.py prepare --run <profile-run> --proposal <saved-generation.json>` で、固定した9入力のhashと送信計画を用意する。
2. `plan --event <元event-id>` で候補・manifest・入力・role/試行番号・モデル/宛先・上限を確認する。
3. 監督者がこの実通信を別途承認したときだけ、planに1時間以内の `expires_at` を加えたowner-only（600）のファイルを渡し、`execute --event <元event-id> --approval <file>` を使う。ファイルの存在だけを人間の同意とはみなさない。
4. `audit --event <元event-id>` はmanifest、元評価、候補、intent、結果、Memory参照を照合する。

結果は元の差分・候補SHA・評価hashへ結び付ける。Memoryは既存schemaの参照記録として別ファイルに保存し、元の#86の監査記録を上書きしない。
合格しても承認票の自動発行や採用処理は呼ばない。実利用検収と運転有効化は #88 の別判断に残る。

## 検証入口

- `python3 -I -B -m unittest discover -s tests -p 'test_semantic_budget.py'`: 最大10回、role3回、二重実行、別eventへの複製、承認と入力の差し替え、401/429、中断、停止・監査、Skill内容を含む模擬比較。
- `python3 -I -B tests/run_semantic_budget_docker.py`: 検証用の別checkoutで、コードとSkillを変えたPUBLIC合成候補を#86でHOLDにし、9つの実Hermesコンテナをnetwork-noneで起動する。認証は合成値、HTTP応答はoffline固定値で、モデル通信・実認証読取は0。
- offline固定応答を意味的な合格として扱わないことも確認する。正の意味的比較は模擬輸送のテストであり、実モデルの改善効果を検収したという意味ではない。
- 標準verify、既存#65/#85/#86の回帰、Bash 5 Security、最新headのGitHub-hosted CI・CodeQL・正式Codexレビューを維持する。固定CI資産は変更しない。
