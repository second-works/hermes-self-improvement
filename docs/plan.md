# 計画書（現行）

この文書を本repoの現行の計画書とする。Issueはこの文書の節をもとに作り、本文に元にした節を書く。
過去の段階計画（[roadmap](roadmap.md)、#61、#105など）は当時の記録として残し、この文書と食い違うときはこの文書を優先する。

合意日：2026-11-18（#114）。

## 1. 目的

Hermesのスキル・ツール・運用手順を、観測 → 診断 → 提案 → 隔離実装 → 評価 → 人間の承認 → 採用 の流れで改善する（#2）。
対象は**本番Hermesのスキル**とする。合成fixtureだけで閉じた改善は、この目的の達成に数えない。

これまでの作り直し（#7 → #31 → #61/#83 → #105）では、どの段階でも本番の `~/.hermes` を対象外にした。そのため、本番スキルは1件も改善されていない。この計画書は、その範囲を目的まで戻す。

## 2. 成果指標

段階2の終わりまでに、次の3つをすべて満たす。

| 指標 | 達成の条件 |
| --- | --- |
| 改善の一巡 | 本番スキル1件以上が、訂正 → 候補 → 評価 → 人間の承認 → 反映 を通る |
| 効果 | 反映した後、同じ種類のタスク3件で、同じ訂正が再発しない |
| 迂回の検知 | 承認を通らない書き込みを、検知の試験で見落とさない |

## 3. 境界

| 対象 | 扱い |
| --- | --- |
| `~/.hermes/skills` | 読み取りを許可する。書き込みは、人間が差分を見て承認したものだけ |
| `~/.hermes` のそのほか（設定、認証情報、会話履歴、memory、サービス） | 読み込み・変更・起動をしない |
| CI（GitHub-hosted runner） | 本番の Hermes へつながない。合成データと模擬応答だけを使う |
| 採用 | 自動では採用しない。反映は必ず人間の承認の後に行う |
| 公開repo | ローカルのパス、ポート、認証の詳細、実データをIssue・PR・logへ出さない |

本番Hermesの設定変更（段階0）は本repoの外で、利用者の確認を得て行う。
この境界は AGENTS.md へ移植する別 Issue で反映する。それまでは、AGENTS.md の現行の境界を守る。

## 4. 本repoの役割

スキルの生成、承認のUI、backup と rollback は、Hermes本体の機能を使い、本repoでは作り直さない。

| 本体に任せるもの | 本体の機能（公開docsで確認。v0.23.x での有無は段階0で照合） |
| --- | --- |
| スキルの生成・更新 | 会話中の学習と、ターン後の background review |
| 承認のUI | `skills.write_approval` と `/skills pending / diff / approve / reject` |
| backup と rollback | curator の snapshot と rollback |

本repoは、本体の外側で足りない次の5つだけを担う。

| 役割 | 内容 | 再利用する資産 |
| --- | --- | --- |
| ① 監査 | スキル変更の git 履歴と差分を残し、承認の記録と照合する | 新規（git の読み取り） |
| ② 評価 | 変更前後のスキルを同じ課題で比べる | `src/evaluation/`。対象が `fixtures/skills/` に固定されている profile を、実スキル向けに一般化する |
| ③ 効果の測定 | 訂正と再発を台帳に記録し、集計する | `src/skill_improvement/`。git を読む側（commits.py）の `~/.hermes` 拒否を、skills に限って緩める。台帳の置き場所は `~/.hermes` の外のまま |
| ④ 迂回の検知 | 承認を通らない書き込み（汎用のファイル書き込みツールなど）を見つける | ①の差分と承認の記録の突き合わせ |
| ⑤ 制御 | 起動、二重実行の防止、停止、利用枠の上限 | `src/manual_cycle/`（実行時間の予算、lock、停止） |

## 5. 安全装置の2区分

変更の種類で装置の重さを分ける。

| 区分 | 判定基準 | 必要な装置 |
| --- | --- | --- |
| 文章だけの変更 | 変更されるファイルがすべて `SKILL.md` などの Markdown で、`scripts/` 配下や実行できるファイルを含まない | git の差分、人間の承認、①の監査記録 |
| コードを含む変更 | 上の条件に当てはまらない変更（スクリプト、実行できるファイル、設定ファイル） | 上に加え、②の隔離評価と、`src/adoption/` 相当の承認の紐づけと復旧の記録 |

判定に迷う変更は、コードを含む変更として扱う。

## 9. 計画書の変え方

- 計画書を変える PR の本文に、1章の目的との差分を書く。何が目的に近づき、何を外すかを明記する。
- 境界（3章）、安全装置の区分（5章）、凍結の解除（8章）を変えるときは、人間の承認を得る。
- 計画書にない変更で止まる決まりは、AGENTS.md へ移植する別 Issue で定める。
