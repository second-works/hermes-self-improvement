## 承認前に実施する検証

新規の隔離checkoutを用い、既存のテストを再利用する。実認証を読み取らず、モデル輸送は模擬、候補とHermesの実行コンテナはnetwork-noneにする。
承認前は実機のLaunchAgentを登録・変更せず、点検入口・dispatcher・停止/再開を検証する。別承認で実施した1回の実機試験の結果は後述し、OS試験と合成検証を区別する。

```sh
python3 -I -B tests/run_skill_profiles_docker.py
python3 -I -B tests/run_periodic_improvement_docker.py
python3 -I -B tests/run_unattended_stop_docker.py
```

前者は登録済みreviewとevent countsの2profileをbaseline/candidate/劣化対照で比較し、有限のコード契約について承認待ちになることを確認する。
後者は保存合成点検から実dispatcherへ渡し、コード＋Skill文候補、意味的評価の別承認、9つの独立Hermes profile、上限、監査、停止/再開、記録保全を確認する。
固定のoffline応答は意味的な正解ではない。9試行完了・全roleの正解数0・control_valid=trueを照合し、INSUFFICIENT_GAINによるHOLD、またはLATENCY_LIMITを併発したREJECTEDを通常の非採用結果として検証する。STOPPED/TIMEOUT、試行欠落、正解数や制御の矛盾、承認待ちへの昇格は成功扱いしない。これを実モデルの改善品質の証拠にしない。
最後の停止試験は、固定ワーカーへ入力も認証も渡さずstdinで待機させ、通常の停止入口から検査済みIDだけを停止する。コンテナ削除、pending解消、停止記録、明示再開後の再送拒否まで確認する。
Docker作成結果が不明な場合も後始末を試み、確認できなければpendingを保持する。
送信中の実HTTP要求の中断やサーバー側の利用量確定を検証した試験ではない。

実公開状態の調査では、改善設定がない新規checkoutで `python3 -I -B scripts/periodic_check.py` を実行する。
GitHubの読取認証だけを使い、モデル認証を読まない。記録した点検がCOMPLETEであり、改善がDISABLEDのままであることを確認する。
公開障害があっても、登録profileへの対応と照合済み再現証跡がなければ実通信の対象にしない。
原本は隔離checkoutの `runs/` に保全し、GitHubには入力本文・正解・個別trace・生logを載せず、[要約証跡](evidence/automation-acceptance-issue88.json)だけを記録する。
