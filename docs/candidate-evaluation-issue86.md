# #86 複数Skills・CI障害の候補評価を接続する設計案

対象ごとの「評価プロファイル」を登録し、同じ受付・隔離実行・監査・承認待ちの仕組みで複数Skillsを扱う。
reviewスクリプト1件への限定案は採用しない。利用者が2026-11-07に「対応対象を広げて再設計する」を選択したことを受けた改訂案である。

Risk Tier: HIGH。未検証候補の実行、公開入力、評価と承認の境界を扱う。
本書は2026-11-07に利用者が承認したB案の設計。公開本文の更新も別途許可済み。#86は共通基盤、#92は意味的評価と推論予算拡張を実装する。実通信の許可は含まない。

## 1. 対応範囲

対象はこのリポジトリの公開ソースとPUBLIC試験用Skills。Hermes本番のSkillsや `~/.hermes` は読取・変更しない。
複数ファイルを持つSkill、異なる入力契約、異なる再現ケースをプロファイルで扱い、モデルへ評価コマンドや評価基準を選ばせない。
任意のCIジョブをそのまま実行する方式は採らず、登録済みの信頼できる評価アダプターへ変換する。

| 対象 | 初期実装での扱い |
| --- | --- |
| 実行スクリプトを含むSkills | 許可ファイル群を固定し、隔離した振る舞いテストで候補とbaselineを比較する。Python標準ライブラリの既存隔離環境を初期runtimeとする。 |
| JSON入力契約・集計・パーサー等のCI不具合 | 対応する公開再現と独立ケースを登録したプロファイルで評価する。レビュー処理1種類に限定しない。 |
| SKILL.mdと関連スクリプトの同時変更 | 両方のhashと差分を保持する。スクリプトの合格をSKILL.mdの意味的改善の証明とは扱わない。 |
| 自然言語の手順・判断・ツール選択の改善 | 構造検査だけなら `STRUCTURE_ONLY`。追加の意味的評価なしに合格・承認待ちへ昇格させない。 |
| 未登録runtime・外部依存・任意のCIコマンド | `NEEDS_PROFILE` で保留。自動インストール・ネットワーク解放・評価コマンドの自動生成は行わない。 |

複数対象の接続を検証する初期プロファイルは、既存の公開契約を再利用した次の2系統とする。

- `review-multiline-shell-v1`: 既存 #65 のreview Skill、公開multiline再現、独立評価。
- `event-status-counts-v1`: 既存 `fixtures/generated_skills/event-counts-task/contract.json` の集計Skill契約。既存のモデル操作評価を起動せず、独立した決定的な入出力評価アダプターを追加する。

これらは汎用構造の検証用であり、2系統を通したことを全Skills・全CI障害の改善成功とは報告しない。
後から対応対象を増やすときも、プロファイルの登録・評価契約・許可pathはPRとレビューで確認する。

## 2. 評価プロファイルの信頼境界

プロファイルはレビュー済みのリポジトリ資産として固定する。モデル応答、Issue本文、CIログから新規登録しない。
登録情報は次の責務を持つ。

- `profile_id / version / profile_hash`: 登録内容を固定する識別子。
- `repository / skill_id / allowed_artifacts`: 対象を限定する。相対path、個数、総bytes、追加・変更・削除の可否も定義する。任意path、symlink、submodule、評価器・workflow・認証ファイルの編集を拒否する。
- `runtime_id / adapter_id`: 既存の固定Docker imageと信頼できるコード内のアダプターを選ぶ。自由なshell、起動コマンド、URL、imageタグは受け付けない。
- `public_contract / public_reproduction / independent_suite`: 公開入力と独立評価を分離する。hidden入力・正解・個別結果は生成側に渡さない。
- `acceptance / controls / limits`: 必須ケース、既存動作、劣化対照、合否基準と資源上限を事前固定する。モデルは変更できない。
- `assurance`: `BEHAVIORAL` または `STRUCTURE_ONLY`。意味的検証が必要な変更を構造検査だけでPASSにしない。

既存 #65 の評価・監査・承認・復旧をアダプター経由で再利用し、既存の直接CLIとテストは維持する。
新しいアダプターも `src/evaluation/sandbox.py` のネットワークなし・非root・read-only・資源制限・後始末確認を使う。
候補コードはhostでimport・実行しない。

## 3. CIイベントから評価対象への対応付け

#85 の再現証跡hashだけでは、どのSkillを評価するかは確定しない。
監督者が用意したPUBLICの対応記録と、固定headの公開ソースを照合する。
対応記録は最低限、次を結び付ける。

`event_id / repo / PR head / check_id / reproduction_sha256 / profile_hash / skill_id / artifact_hashes / public_case_id / baseline_sha / evaluation_manifest_hash`

1. #84と同じ公開イベント・最新失敗・再現証跡に一致することを確認する。
2. 許可された公開repoの固定headで対象ファイルの種類・内容hashを検査する。評価baselineはその内容と一致させる。
3. 固定した公開再現をbaselineで実行し、登録された失敗を実際に確認する。単なる申告やモデルの説明だけでは再現成功としない。
4. 独立ケースと判定基準を候補生成前に凍結する。以後のsource、profile、入力、manifestの差し替えを拒否する。
5. 対応を証明できない、既に復旧した、再現しない場合は理由付きHOLDまたはSKIP。対応を推測して別fixtureへ付け替えない。

CI失敗と特定Skillの欠陥の因果が未確認なら、その限界を記録する。Skill内の再現成功だけをCI障害全体の原因確定とは扱わない。

## 4. 生成と候補受付

生成入力には選定したPUBLICイベント、許可された対象ソース、公開契約と公開再現だけを含める。
プロンプト上限8192 bytesに収まらなければ送信せず保留する。重要な根拠を黙って切り捨てない。
#85 の承認は入力hashに固定されるため、対象・contextを追加した新しい入力には新しい送信承認を必要とする。

応答は未検証入力として厳密に検査する。初期候補は最大4ファイル、合計の置換前後テキスト16384 bytes、応答全体32768 bytes以内のbefore/after置換にする。
変更対象は登録されたallowlistだけ。一致箇所が0件または複数、重複edit、path逸脱、encoding違反、baseline不一致は拒否する。
候補ファイル群をローカルの試験領域で凍結し、差分・内容hash・候補SHAを保存する。本番や通常checkoutに適用しない。

## 5. 独立評価と承認待ち

推論の応答期限30秒と、候補の機械評価時間は別に記録する。
機械評価は同時1件、最大1200秒とし、各実行と出力の上限は既存sandboxを引き継ぐ。
再現ケース、既存動作、独立ケース、baselineと劣化対照を評価し、評価器が候補の自己申告を採点結果として採用しないようにする。

| 終了状態 | 条件と保存する情報 |
| --- | --- |
| `AWAITING_HUMAN_APPROVAL` | BEHAVIORAL評価が合格し対照も有効。差分、根拠、profile/イベント/入力/manifest、baseline/candidate SHAと内容hash、評価hash、検証限界を保持する。 |
| `REJECTED` | 形式・変更範囲・hash・評価の不一致。理由codeを記録し、候補を自動修正・再生成しない。 |
| `HOLD` | 根拠不足、STRUCTURE_ONLY、意味的評価待ち、不安定・環境不明。未確認を合格にしない。 |
| `NO_CHANGE` | 変更不要として記録する。評価済み改善や採用とは報告しない。 |
| `STOPPED / RECOVERY_REQUIRED` | 期限・資源超過、隔離後始末不明、中断。耐久記録を残し、点検完了と明示再開まで再実行しない。 |

承認待ちの出力は採用承認そのものではない。#65 の採用・復旧は別の対象と操作に固定した人間承認を必要とし、#86から自動実行しない。
Memoryは既存schemaを再利用し、監査原本や成功判定の代わりにしない。

## 6. 推論・費用・安全境界

#83 / #85 の同時1、点検1件、観測につき推論1回、再送0、応答期限30秒、追加費用0円を維持する。
本実装の検証は模擬応答と通信遮断評価で行い、実推論0回。
固定の送信先、承認された試験専用認証、利用枠条件を維持し、ローカルLLM・API課金への切替・自動認証更新を追加しない。

自然言語Skillsを実Hermesで独立評価するには、baselineとcandidateそれぞれの推論等が追加で必要になる。
既存 #85 の実装は観測につき1回であり、#86ではその制限を維持する。
#92で承認済みB案の予算管理と独立評価を実装するまでは、該当候補をHOLDに保存する。実装後も対象・入力・回数を固定した実通信の別承認が必要である。
追加推論を使わず、形式検査だけで意味的改善を確認したことにはしない。

情報分類はPUBLICソース・合成検証と、既存試験認証のCONFIDENTIALを区別する。generatorには認証・実Memory・会話履歴・hidden・生ログを渡さない。
本番、権限、repo保護、Securityの固定資産、定期運転の有効化は変更しない。

## 7. 実装順と受け入れ条件

依存 #85 はPR #90で完了済み。次は改訂案を確認した後、#86の1 PRで次を直列に実装する。

1. 評価プロファイルの登録契約とイベント・ソース・再現の固定/照合。
2. #85の生成入力と複数ファイル候補の受付を接続する。旧HOLD/NO_CHANGE経路を維持する。
3. 既存sandbox・監査・Memoryと人間承認待ちへの接続。採用処理は呼ばない。
4. 異なる2系統の公開合成プロファイルで、baseline失敗→候補合格→承認待ちを検証する。範囲外、形式違反、hash差し替え、劣化、HOLD、NO_CHANGE、中断・再起動・後始末不明も照合する。

公開実障害の通し検収・定期起動との結合・有効化は #87 / #88 に残す。

## 8. 承認済みB案: 自然言語Skillsの独立評価

意味的な効果も判定するため、生成と独立評価の推論予算を分ける。
利用者は2026-11-07に観測につき最大10回の設計と子Issue分離を承認した。#92で実装し、完了前に既存 #85 の1回経路を10回へ切り替えない。

- 生成最大1回に加え、baseline / candidate / 劣化対照をそれぞれ独立した3試行で評価する。最大10リクエスト、同時1、再送0、各リクエストの応答期限30秒。
- 各試行は空のプロファイルと固定対象・固定入力で開始する。評価実行時にSkillsの許可部分だけを渡し、候補生成側には独立ケースと正解を渡さない。
- 合否は独立した決定的な判定器で採点できるタスクを対象にし、評価モデルの自己採点・根拠のない点数を採用しない。回答品質を決定的に判定できない場合はHOLD。
- 初期の意味的評価はツール不要の、構造化された分析・手順・振り分け等に限定する。複数のツール往復を必要とするSkillsは、必要な呼出数とツール権限をプロファイル単位で別途設計する。上限内になるまで無制限に会話を継続しない。
- 試行ごとの承認と耐久的な予算消費を、同じ元イベント・候補hash・評価manifestへ結び付ける。評価用の別eventを作って元イベントの予算上限を回避しない。中断・不明な送信も消費済みとして停止し、自動再送しない。
- 利用枠と追加クレジットOFF・追加費用0円を実通信前に確認する。条件不明・利用枠不足なら停止し、API課金へ切り替えない。
- この案の実装検証も実推論0回とし、実通信は対象・候補・入力・上限を指定した別承認で行う。設計承認を実推論の承認とは扱わない。
