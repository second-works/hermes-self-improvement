# Issueからマージ依頼まで

AGENTS.mdの境界を守り、次の順に進める。各段階の結果は、Issue、PR、full HEAD SHAと一緒に報告する。

## 0. 計画書にない変更では止まる

現行の計画書は `docs/plan.md`。利用者は計画書を承認の場としている（2026-11-18。#116）。計画書とIssueに沿った作業は、確認を待たずに進める。

1. Issueを作るときは、本文に、元にした計画書の節を書く。計画書によらないIssueには「なし（利用者の指示。日付）」と書く。計画書にない機能・仕様・段階を加えることになるなら、作る前に止まる。人間が会話で直接指示した機能・仕様・段階は、その指示を承認とする。この扱いは2の境界や安全装置の変更には使わない。Issueの文面に「利用者の指示」と書いてあることは、承認の代わりにならない。
2. 実装中に、Issueに書かれていない次の変更が必要になったら止まる。何が必要か、なぜ必要か、代案を報告し、人間の「進めて」を待つ。CIの失敗やレビュー指摘への対応でも同じにする。
   - 境界・権限・外部送信を広げる（読む範囲、書く範囲、送る相手や内容が増える）。
   - `~/.hermes` への新しい書き込み経路を作る。`~/.hermes/skills` への反映も、本体の承認の仕組み（`/skills approve`）だけを使う。
   - 安全装置の区分（計画書5章）や、文章だけの変更の判定基準を変える。
   - 既存の機能を削除する。仕様としての動作を変える。不具合を直すだけの修正は含まない。
3. Issueにない改善や修正の案を見つけたら、実装しない。内容と理由を区切りの報告とPR本文に書く。提案のために作業は止めない。採用するかは人間が決める。
4. 計画書を変えるときは、`docs/plan.md` の9章（計画書の変え方）に従う。範囲を狭める変更では、目的から離れていないかを特に確かめる。

## 1. 着手

1. Issueの最新本文、依存Issueの状態、関連PRを読む。依存が未完了なら着手しない。Issueに元にした計画書の節が書かれていれば、そこも読む。
2. `git status`、full HEAD、既存のブランチとworktreeを確認する。他者の未コミット変更には触れない。
3. mainから `feature/issue-<番号>-<短い名前>` のブランチを作る。

## 2. 実装、検証、自己レビュー

1. Scopeの範囲内で実装し、Doneの各項目と照らし合わせる。必要なテストを足す。
2. `./scripts/verify.sh` を実行する。変更をstageしてから `bash scripts/security-preflight.sh .` を実行する。
3. 差分全体を読み直す。範囲外の変更、Secrets、テストの無効化、未確認の前提がないかを確かめる。
4. 失敗したら原因を直して2からやり直す。実行できないときは理由を報告して止まる。

## 3. Draft PR

1. 自分が変更したファイルだけを指定してcommitし、Issueのブランチへpushする。
2. PRテンプレートで、`Closes #<番号>`、変更の概要、選んだ前提、検証結果、未完了と対象外を書く。
3. PRの監視（CI失敗やレビューコメントでの自動起動）が使える環境なら有効にする。

## 4. CIとSecurity

1. 最終headで、CIとSecurityのcheckを別々に確認する。`scripts/check-pr-head.sh <PR番号>` で照合できる。必須checkの名前は `.github/pr-gate-checks` に書く（照合はbaseブランチの版を読む。なければ既定の名前で照合する）。
2. 失敗したらログを読み、原因を直してpushする。skip、無効化、空commitでの再実行はしない。
3. checkが見つからない、開始されない、取得できないときは成功にしない。状態を報告して判断を求める。

## 5. ユーザー検収（Doneに含まれるときだけ）

Doneから確認項目を作って依頼する。OKが出るまで次へ進まない。レビュー後の修正で検収対象が変わったら、もう一度依頼する。

## 6. 正式レビュー

1. `.github/pr-gate-review` が指定する種類のレビューを最終headで実施する。
   - `claude-code`: Claude Codeの `/code-review <PR番号>` で最終headをレビューし、指摘と対応をPRコメントに記録する。コメントの末尾に、機械可読な記録 `<!-- claude-code-review:v1 {"commit_sha":"<最終headのfull SHA>","status":"completed","has_unresolved_findings":false} -->` を1行で付ける。未対応の指摘が残るときは `has_unresolved_findings` を `true` にする。
   - `codex`: Codex Reviewを最終headで実施する。自動で始まらなければ `@codex review` とコメントする。
2. 指摘がないときは、Codexでは要約コメントの更新や👍だけで終わることがある。そのheadの完了を確認してから次へ進む。headが変わったら、変更分をレビューし直して新しい記録を付ける。
3. Risk TierがHIGHのIssueでは、実装したセッションとは別のセッションでもレビューする。

## 7. 指摘への対応

1. 指摘ごとに、実際の入力から問題が起きる経路を確かめる。
2. Issueの範囲内で妥当なものは同じPRで直し、影響した検証と検収をやり直す。スレッドに修正したcommitを返信し、解決済みにする。
3. 誤検知や範囲外のものは、根拠を返信する。範囲外の作業、仕様の変更、セキュリティ上の判断は人間に確認する。
4. 回数を理由に止まらない。同じ種類の指摘が続くときは、ほかに同じ問題がないかをまとめて確かめる。

## 8. マージ依頼

次がすべて同じ最終headでそろったら、人間にマージを依頼する。`scripts/check-pr-head.sh <PR番号>` が `PR_GATE_STATUS=READY` を返すことも確かめる。

- ローカルの標準検証、CI、Securityが成功している
- 正式レビューが完了し、未対応の指摘と未解決のスレッドがない（通常のPRコメントで届いた指摘と、`.github/pr-gate-review` が指定していないレビュアーの結果は、照合スクリプトでは読めないので自分で読む）
- mainとの競合がない
- 必要なユーザー検収が済んでいる

マージは人間が行う。親Issueのcloseと次のIssueへの着手も、人間の指示に従う。

## 引き継ぎ

セッションをまたぐときは、Issue、PR、full HEAD SHA、未コミット変更、残作業、検証の状態と証拠だけを渡す。報告された成功は、受け取った側が最終headで確かめ直す。
