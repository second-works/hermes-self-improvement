# 計画書（現行）

この文書を本repoの現行の計画書とする。Issueはこの文書の節をもとに作り、本文に元にした節を書く。
過去の段階計画（[roadmap](roadmap.md)、#61、#105など）は当時の記録として残し、この文書と食い違うときはこの文書を優先する。

合意日：2026-11-18（#114）。

## 1. 目的

Hermesのスキル・ツール・運用手順を、観測 → 診断 → 提案 → 隔離実装 → 評価 → 人間の承認 → 採用 の流れで改善する（#2）。
対象は**本番Hermesのスキル**とする。合成fixtureだけで閉じた改善は、この目的の達成に数えない。

これまでの作り直し（#7 → #31 → #61/#83 → #105）では、どの段階でも本番の `~/.hermes` を対象外にした。そのため、本番スキルは1件も改善されていない。この計画書は、その範囲を目的まで戻す。

## 2. 成果指標

段階2の終わりまでに、次の3つをすべて満たす。

| 指標 | 達成の条件 |
| --- | --- |
| 改善の一巡 | 本番スキル1件以上が、訂正 → 候補 → 評価 → 人間の承認 → 反映 を通る |
| 効果 | 反映した後、同じ種類のタスク3件で、同じ訂正が再発しない。「同じ種類のタスク」の定義と対象の3件は、反映の前に人間が決めて③の台帳に記録する。再発したかどうかは人間が判定する |
| 迂回の検知 | 承認を通らない書き込みを、検知の試験で見落とさない |

## 3. 境界

**状態：有効（#116 で AGENTS.md に反映）。** `~/.hermes/skills` を読むコードや手順は、計画書の段階に沿ったIssueの中だけで作る。段階0の完了より前に、本repoから読む経路を作らない。

| 対象 | 扱い |
| --- | --- |
| `~/.hermes/skills` の読み取り | 段階0の完了後に、段階に沿ったIssueの中だけで許可する。段階0の完了は、6章に完了日が書かれたことで判断する |
| `~/.hermes/skills` の symlink | 指す先がどこでもたどらず、読まず、複製しない。`~/.hermes/skills` そのものが symlink のときも読まない |
| `~/.hermes/skills` の git の記録 | 次をすべて満たす方法だけで読む。その方法を段階1で試験して確かめるまでは読まない。<br>・`.git` へ書き込まない<br>・そのrepoの設定、attributes、hookを使わない<br>・gitfile や alternates で、ほかの場所を読まない |
| `~/.hermes/skills` の変更 | スキルの中身の変更（反映）は、本体の承認の仕組み（`/skills approve`）を通したものだけ。本repoのコードやエージェントは直接書き換えない。git の管理（init、commit、戻す操作）は人間が本repoの外で行う |
| そのほか | `~/.hermes` のそのほか（設定、認証情報、会話履歴、memory、サービス）は、読み込み・変更・起動しない。`~/.hermes` の外にある本番設定、認証情報、サービス（launchd の設定、ほかの設定用のフォルダ、キーチェーンなど）も同じ |
| CI（GitHub-hosted runner） | 本番の Hermes へつながない。合成データと模擬応答だけを使う |
| 採用 | 自動では採用しない。反映は必ず人間の承認の後に行う |
| 公開repo | ローカルのパス、ポート、認証の詳細、実データをIssue・PR・logへ出さない |

本番Hermesの設定変更（段階0）は本repoの外で、利用者の確認を得て行う。
security-model.md の「隔離評価にホストの HOME や `~/.hermes` を渡さない」は残す。評価には、対象のスキルのファイルだけを複製して渡す。
機能ごとの文書にある `~/.hermes` の禁止は、その機能の今の制約として残す。たとえば skill-improvement-mvp.md 11章、manual-cycle.md、change-intake スキルがそうである。変えるときは、段階のIssueで、コードと一緒に直す。

## 4. 本repoの役割

スキルの生成、承認のUI、backup と rollback は、Hermes本体の機能を使い、本repoでは作り直さない。

| 本体に任せるもの | 本体の機能（公開docsで確認。v0.23.x での有無は段階0で照合） |
| --- | --- |
| スキルの生成・更新 | 会話中の学習と、ターン後の background review |
| 承認のUI | `skills.write_approval` と `/skills pending / diff / approve / reject` |
| backup と rollback | curator の snapshot と rollback |

本repoは、本体の外側で足りない次の5つだけを担う。

| 役割 | 内容 | 再利用する資産 |
| --- | --- | --- |
| ① 監査 | スキル変更の git 履歴と差分を残し、承認の記録と照合する | 新規（git の読み取り） |
| ② 評価 | 変更前後のスキルを同じ課題で比べる | `src/evaluation/`。対象が `fixtures/skills/` に固定されている profile を、実スキル向けに一般化する |
| ③ 効果の測定 | 訂正と再発を台帳に記録し、集計する | `src/skill_improvement/`。git を読む側（commits.py）の `~/.hermes` 拒否を、skills に限って緩める。台帳の置き場所は `~/.hermes` の外のまま |
| ④ 迂回の検知 | 承認を通らない書き込み（汎用のファイル書き込みツールなど）を見つける | ①の差分と承認の記録の突き合わせ |
| ⑤ 制御 | 人が始める実行の起動手順、二重実行の防止、停止、利用枠の上限。定期実行などの自動起動は含まず、入れるときは計画書を変えて承認を得る | `src/manual_cycle/`（実行時間の予算、lock、停止） |

## 5. 安全装置の2区分

変更の種類で装置の重さを分ける。

| 区分 | 判定基準 | 必要な装置 |
| --- | --- | --- |
| 文章だけの変更 | 変更されるファイルがすべて `SKILL.md` などの Markdown で、`scripts/` 配下や実行できるファイルを含まない。さらに、コードブロックやコマンドの追加・変更、frontmatter（使うツールや設定）の変更を含まない | git の差分、人間の承認、①の監査記録 |
| コードを含む変更 | 上の条件に当てはまらない変更（スクリプト、実行できるファイル、設定ファイル） | 上に加え、②の隔離評価と、`src/adoption/` 相当の承認の紐づけと復旧の記録 |

判定に迷う変更は、コードを含む変更として扱う。
文章だけの変更でも、エージェントの振る舞いは変わる。悪化は③の効果の測定で見つけ、人間が curator の rollback か git で戻す。

## 9. 計画書の変え方

- 計画書を変える PR の本文に、1章の目的との差分を書く。何が目的に近づき、何を外すかを明記する。
- 計画書のどの章の変更も、人間の承認を得てからマージする。成果指標（2章）や段階の完了条件（6章）を緩める変更は、緩める理由も書く。
- 計画書にない変更で止まる決まりは、AGENTS.md の「計画書にない変更では止まる」と、steward スキルの0節にある（#116）。
