# 計画からIssueへ

合意した計画を、実装者が推測せずに進められるIssueにする。登録したら、このSkillの作業は終わる。

## 1. 合意を固定する

会話、計画書、ユーザーの指示から、目的、採用した方針、Scope、Non-goals、成功条件、依存、未決事項を短く整理する。確定している内容は再質問しない。

## 2. 未決事項を確かめる

次のどれかが決まっていなければ、登録せずに必要な判断だけを示して止まる。

- Scopeや成功条件が決まらず、Issueの分け方が変わる
- 依存関係が分からず、順番を決められない
- UI、データ移行、Security、本番などの重要な判断を推測する必要がある
- 対象のrepositoryを特定できない

調査しないと決められない事項は、調査用のIssueとして分ける。

## 3. 分け方を決める

- 複数のPRに分かれるときは、親Issueをロードマップにし、実装は子Issueへ分ける。子Issueは1つにつき1 PRとする。
- 1 PRで終わるときは、親Issueを作らず単一のIssueにする。
- 同じ重要ファイルを触る子Issueは、根拠なく並列にしない。

## 4. 本文を書く

`.github/ISSUE_TEMPLATE/` の親子テンプレートを使う。子IssueはGoal / Context / Scope・Boundaries / Non-goals / Done / Verification / Dependenciesの7項目とする。

- Risk Tier（LOW / MEDIUM / HIGH）と理由を、Scope・Boundariesに1行で書く。安全への影響が分からなければHIGHとする。
- Doneは、実装の手順ではなく、確認できる結果として書く。
- Verificationには、必要な正常系、異常系、回帰の確認方法を書く。全観点の空欄は作らない。
- UIやSecurityなどの専門の欄は、該当するときだけ書く。親と子に同じ詳細を複製しない。

## 5. 登録する

ユーザーが登録を依頼したときだけGitHubへ書き込む。案の提示だけを求められたら登録しない。

1. 親Issueを登録する。
2. 親の実際の番号を使って子Issueを登録する。
3. 子の実際の番号で、親の子Issue一覧と依存の順番を更新する。番号は推測しない。

## 6. 登録後

ブランチ作成、実装、PR作成、マージ、次のIssueへの着手はしない。登録したIssue、Risk Tier、実装の順番、登録しなかった事項を報告する。
