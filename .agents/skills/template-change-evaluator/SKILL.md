# Template Change Evaluator

外部の新しい考え方を「新しいから」追加せず、現行テンプレートが解決している責務と比較して、必要な変更だけを選ぶSkill。

## 原則

- 採否を決める前に、必ず現行repoを確認する。
- 新規性ではなく、解決する具体的な失敗モードと再利用頻度で評価する。
- 既存の正本、Gate、Skill、script、test、CIと同じ責務を重複して作らない。
- 決定論的に検査できる処理は、原則としてSkillではなくscript / test / CIへ置く。
- 今回だけの要求や判断値は、共通Ruleへ昇格させずIssue / PRへ置く。
- Safety / Security / Review / Human Approval Boundaryを、簡素化やコストだけを理由に弱めない。

## 1. 評価対象を固定する

提案、記事、技術、運用改善について、少なくとも次を短く整理する。

- 何を追加・変更しようとしているか
- どの失敗や運用負荷を減らす想定か
- どの作業で繰り返し使う想定か
- テンプレート全体の共通責務か、案件固有の要求か

単純な紹介・要約だけが目的なら、このSkillの変更評価はそこで終了する。

## 2. 現行repoを先に確認する

採用案を作る前に、対象責務が既に存在しないか検索する。少なくとも関連する範囲で次を確認する。

- `AGENTS.md`: 常時必要な停止条件、routing、共通ルール
- `docs/`: 詳細仕様、設計判断、Gateの正本
- `.agents/skills/`: 反復する非決定論的な実行手順
- `scripts/` / `templates/`: 決定論的処理、生成物の雛形
- `tests/`: 機械判定できる契約と回帰
- `.github/workflows/`: CI / Security / lifecycle automation
- `.github/ISSUE_TEMPLATE/` / PR template: 今回値の入力契約
- 既存Issue / PR: 進行中または却下済みの同目的変更

名前一致だけでなく、**同じ失敗モードを既に別の仕組みが解決していないか**を見る。

## 3. 採用価値を評価する

次を確認する。

1. 具体的な失敗モードがあるか。
2. その失敗モードは複数案件・複数回で再発し得るか。
3. 現行の仕組みだけでは不足するか。
4. 新しい仕組みで責務が二重化しないか。
5. 追加後の更新・参照・実行コストに見合うか。
6. より小さい変更、既存Ruleの明確化、script / testへの機械化で足りないか。

## 4. 必ず5分類する

評価結果は次のいずれか1つを主分類として示す。

- `ALREADY_COVERED`: 現行テンプレートで実質対応済み。新規追加しない。
- `ADOPT`: 既存責務と競合せず、そのまま追加する価値がある。
- `ADAPT`: 考え方は有用だが、現行アーキテクチャへ合わせて小さく変形して取り込む。
- `REJECT`: 重複、過大、失敗モード不明、運用負荷過大、安全境界との不整合などで採用しない。
- `FOLLOW_UP`: 現時点では追加せず、利用頻度、失敗事例、Tool能力などの条件成立後に再評価する。

部分ごとに分類が異なる場合は、主分類に加えて項目別分類を示してよい。

## 5. 配置先を決める

採用する項目は、責務に応じて次の配置を選ぶ。

- `AGENTS`: 毎回必要な共通境界、短いrouting、停止条件
- `docs`: 条件発生時に参照する詳細仕様・設計・Gateの正本
- `Skill`: AIが判断を含めて繰り返す特定作業の実行手順
- `script`: 入出力が決まり機械的に再現できる処理
- `test`: 契約、存在、回帰、禁止条件の決定論的検証
- `CI`: commit / PR等のlifecycleで自動実行すべき検証
- `ISSUE_ONLY`: 今回だけの要求、Acceptance、Design Decision、案件固有値

複数層を使う場合も正本は1つにし、他の層は短い入口・実行・検証に限定する。

## 6. 次アクションを決める

- `ALREADY_COVERED` / `REJECT`: 原則として変更しない。既存の該当箇所を示す。
- `FOLLOW_UP`: 再評価条件を示し、今回の実装へ追加しない。
- `ADOPT` / `ADAPT`: 最小変更範囲、Non-goals、配置先、テスト責務、Risk Tierを整理する。
- ユーザーがIssue化・実装まで依頼している場合だけ、既存のPlan Review / Issue Quality /実装フローへ接続する。評価依頼だけで自動的にmain変更やMergeを行わない。

## 停止条件

次の場合は推測で採用へ進めない。

- 現行repoを十分に確認できず、既存責務との重複を判断できない。
- Safety / Security / Review / Production / Human Approval Boundaryの意味変更を伴うが、設計判断が未確定。
- 共通テンプレートへ昇格させるだけの反復性や失敗モードを説明できない。
- 採用先の正本が複数候補に分裂し、どこがauthoritativeか決められない。

## 標準出力

簡潔に次を示す。

- **Decision**: 5分類
- **Existing coverage**: 現行repoで既に担っている責務
- **Failure mode / frequency**: 解決する失敗と再利用性
- **Placement**: `AGENTS / docs / Skill / script / test / CI / ISSUE_ONLY`
- **Change scope / Non-goals**: 採用する場合の最小範囲
- **Next action**: 変更なし / 再評価 / Issue化候補 / 実装フローへ接続
