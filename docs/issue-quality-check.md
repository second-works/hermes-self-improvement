# 子Issue妥当性チェック基準

Nine標準AI開発フローでは、子IssueをGitHubへ登録する前に品質チェックを行う。

目的は、CodexがIssue単位で安全に実装でき、1 Issue = 1 PRでレビュー可能な状態にすること。


最小IssueのGoal、Scope / Boundaries、Done・Verification、1 PRの実装単位、Dependenciesは以下の6 MUSTへ対応する。ContextとNon-goalsも入力契約に残す。Risk Tierと理由、安全境界は短く記録し、非該当のUI / Framework / State / Harnessの専門欄は要求しない。重要な条件が不明なら省略で補わず停止する。

## 判定対象と判定順

子Issueは、まず次のMUSTをすべて満たす必要がある。1つでも欠落した場合は、ScoreにかかわらずGitHub登録・実装開始を停止し、Issueを補完、分割、統合、または依存関係を整理する。

1. **目的**: 達成したい目的が1つに明確化されている。
2. **変更範囲**: 変更するディレクトリ、モジュール、主要ファイルを予測できる。
3. **独立検証**: Issue単体の完了条件とテストまたは手動確認手順がある。
4. **1 PR**: 変更が1つの目的としてレビュー可能である。
5. **依存関係**: 依存Issue、直列化、または並列実装可能な根拠が明記されている。
6. **安全境界**: Security Boundary、Human Approval、Secrets、権限、Productionへの影響と制御を説明できる。

テストを追加・更新・統合・削除するIssueは、検証責務、適切なテスト種別、削除時の保証先もMUSTとして明記する。認証・認可、入力検証、Repository境界、重要な回帰テスト、必要なIntegration / E2Eの安全網を根拠なく失わない。

次はSHOULDである。欠落しても停止せず、読みやすさを改善する候補として記録する。

- 背景、利用者への影響、補足例が読みやすく記されている。
- 分割・統合・並列化を選んだ理由が具体例とともに説明されている。

## 補助Score

ScoreはMUSTを代替しない補助表示である。各MUST観点を0〜2点で記録する場合、許容値は0、1、2だけとし、合計範囲は0〜12点とする。範囲外の値を有効評価に使わない。

- 2点: 明確で問題なし
- 1点: 実装可能だが補足が必要
- 0点: MUST不足として停止

Scoreが高くてもMUST不足は登録・実装開始を許可しない。SHOULDだけの不足は改善候補として継続できる。

## 分割・統合・依存関係の判断

目的、変更範囲、独立検証、1 PR、依存関係、安全境界のいずれかを満たせない場合は、分割・統合・設計Issue・直列化を検討する。依存Issueが未完了で安全に実装できない場合は直列化する。

# 分割するべきサイン

次のどれかに該当する場合は分割を優先する。

- タイトルに「〜と〜」が複数並ぶ
- 完了条件が異なる機能群に分かれている
- API、DB、UI、インフラを一度に大きく変更する
- 別々にロールバックしたくなる変更が混ざっている
- テスト方法が複数の独立機能に分かれる
- PRレビュー担当を分けたくなる

# 統合するべきサイン

細かくしすぎたIssueは統合する。

- 単独ではユーザー価値も技術的完了もない
- 数行の変更だけで別Issueにする意味が薄い
- 必ず同じPRで変更しなければ動作しない
- 完了条件・テスト・変更ファイルがほぼ同じ

# 子Issue作成前の標準工程

```text
計画書
  ↓
仮の子Issue作成
  ↓
6つのMUSTを確認
  ↓
分割 / 統合 / 依存関係修正
  ↓
MUST不足がなければ登録
  ↓
GitHubへ登録
  ↓
Codex実装
```

# ChatGPTがIssue化する際の標準ルール

「Nine標準AI開発フローでIssue化して」と依頼された場合、GitHubへ登録する前に各子Issueをこの基準で評価する。

問題があるIssueは、そのまま登録せず、分割・統合・依存関係の整理を行う。

各子Issueには原則として以下を含める。

- 目的
- 実装内容
- やらないこと
- 変更してよい範囲
- 原則変更しない範囲
- 完了条件
- テスト条件
- 依存Issue
- 並列実装可能かどうか

テスト削除を含むIssueでは、テスト条件に「削除対象が担っていた検証責務」と「削除後にその責務をどこで保証するか」を明記する。

最終目標は、CodexがIssue本文だけを読んでも作業範囲と終了条件を判断できる状態にすること。

### Child Issue Quality Gate

子IssueはGitHub登録・Codex実装前に [`docs/issue-quality-check.md`](issue-quality-check.md) のMUSTを確認する。

- MUST: 目的、変更範囲、独立した完了判定とテスト、1 PRでのレビュー可能性、依存関係、安全境界。
- MUSTが1つでも欠落した場合はScoreにかかわらず登録・実装開始を停止し、補完、分割、統合、または依存関係を整理する。
- SHOULD: 読みやすさ、背景、補足例。SHOULDのみの不足は改善候補として継続できる。
- Scoreは補助表示であり、許容値は各観点0〜2点、合計0〜12点に限る。高ScoreでもMUST不足を打ち消さない。
